# Cineplex Showtime API Discovery and Smoke-Test Specification

## 1. Objective

Create a small, disposable exploration project that determines whether Cineplex exposes a publicly callable web endpoint that can answer:

> Are tickets or public showtimes currently available for a specified movie at a specified Cineplex theatre, optionally filtered by presentation format such as IMAX?

The initial test case is:

- Movie: **The Odyssey**
- Theatre: **Scotiabank Theatre Toronto**
- Presentation format: **IMAX**
- Desired result: Determine whether one or more publicly bookable screenings exist, and return enough stable identifying information to detect when a new screening first appears.

The implementation must be reusable for:

- Any Cineplex movie
- Any Cineplex theatre
- Any presentation format
- Any date or date range

This is an exploration and smoke-test project, not yet a production monitoring service.

---

## 2. Primary Questions to Answer

The smoke test must answer the following questions with evidence.

1. Does the current Cineplex website use one or more JSON endpoints to retrieve:
   - Movies
   - Theatres
   - Bookable dates
   - Showtimes or sessions
   - Presentation formats
   - Booking URLs

2. Can those endpoints be called:
   - Without authentication
   - Without a Cineplex account
   - Without browser cookies
   - From a server-side script
   - Using only normal HTTP headers

3. Which identifiers are required?
   - Film ID
   - Theatre ID, location ID, or site ID
   - Date
   - Language or market
   - Experience or presentation-format ID

4. Can the returned data distinguish:
   - IMAX from standard screenings
   - IMAX 70mm from digital IMAX, when applicable
   - Available sessions from sold-out or unavailable sessions
   - A listing page from a genuinely bookable session

5. What field or combination of fields can serve as a stable screening identifier for change detection?

## 3. Important Constraints

### 3.1 Do not assume an endpoint is current

Historical Cineplex-related projects have referenced endpoints such as:

```text
https://www.cineplex.com/api/v1/theatres
https://www.cineplex.com/api/v1/movies
https://www.cineplex.com/api/v1/movies/{movieId}/availabletheatres/dates
https://api.cineplex.com/api.svc/FeaturedNowPlayingAndComingSoon/
```

These are only discovery candidates. Do not build the solution around them unless they are verified against the current Cineplex website.

### 3.2 Prefer the current web application’s data source

The authoritative source for discovery is the network traffic generated by the current Cineplex website.

Use, in order of preference:

1. Current browser network requests
2. URLs and configuration embedded in current JavaScript bundles
3. Current page source and hydration data
4. Historical open-source implementations
5. HTML parsing only as a fallback

### 3.3 Do not automate ticket purchasing

This project must only:

- Read public movie and showtime information
- Identify new publicly bookable sessions
- Produce structured output

Do not:

- Log into Cineplex
- Reserve seats
- Add tickets to a cart
- Bypass queues, CAPTCHAs, authentication, rate limits, or access controls
- Call checkout or payment endpoints

### 3.4 Minimize traffic

During exploration:

- Make individual manual requests
- Do not run a frequent polling loop
- Cache discovery responses locally
- Add at least one second between exploratory requests
- Stop testing if the server returns `429`, CAPTCHA content, or an explicit block

## 7. Phase One: Locate the Correct Public Pages

### 7.1 Find the movie page

Attempt to locate the current Cineplex page for the configured title.

Acceptable methods:

1. Cineplex’s own search page
2. Current Cineplex movie listing pages
3. Search-engine discovery as a fallback
4. A manually supplied `CINEPLEX_MOVIE_URL`

Record:

```json
{
  "requestedTitle": "The Odyssey",
  "matchedTitle": null,
  "moviePageUrl": null,
  "cineplexFilmId": null,
  "matchConfidence": null
}
```

Do not silently accept an approximate title match.

### 7.2 Find the theatre page

Locate the current Cineplex page for:

```text
Scotiabank Theatre Toronto
```

Record:

```json
{
  "requestedTheatre": "Scotiabank Theatre Toronto",
  "matchedTheatre": null,
  "theatrePageUrl": null,
  "cineplexTheatreId": null,
  "locationId": null,
  "siteId": null,
  "matchConfidence": null
}
```

Distinguish this theatre from similarly named Scotiabank theatres in other cities.

The Toronto address or city must be validated before accepting the match.

## 8. Phase Two: Discover Current Network Endpoints

Implement `discover-network.ts` using Playwright.

### 8.1 Browser behaviour

The script must:

1. Launch Chromium.
2. Open a fresh browser context.
3. Register request and response listeners before navigating.
4. Visit the current movie page.
5. Visit the current theatre page.
6. Interact only as necessary to expose showtimes:
   - Accept or dismiss cookie consent
   - Select Toronto
   - Select Scotiabank Theatre Toronto
   - Select an available date
7. Capture relevant requests and responses.

### 8.2 Capture criteria

Record requests or responses whose URL, request body, response content type, or response body contains terms such as:

```text
movie
movies
film
films
theatre
theater
location
showtime
showtimes
session
sessions
performance
performances
bookable
booking
dates
experience
format
imax
vista
site
cinema
```

Prioritize responses with these content types:

```text
application/json
application/graphql-response+json
text/json
```

Also capture:

- GraphQL requests
- XHR requests
- Fetch requests
- JSON embedded in HTML
- Next.js or similar hydration payloads
- API base URLs in JavaScript configuration

### 8.3 Save network observations

Write sanitized observations to:

```text
output/network-observations.json
```

Each observation should contain:

```json
{
  "timestamp": "ISO-8601 timestamp",
  "pageUrl": "page that initiated the request",
  "method": "GET",
  "url": "full request URL",
  "resourceType": "xhr",
  "requestHeaders": {},
  "requestBody": null,
  "status": 200,
  "responseContentType": "application/json",
  "responseHeaders": {},
  "responseBodySample": {},
  "candidatePurpose": "showtimes",
  "containsMovieTitle": true,
  "containsTheatreName": true,
  "containsImax": true
}
```

### 8.4 Redaction

Before saving anything, redact:

- Cookie values
- Authorization headers
- Session identifiers
- Device identifiers
- Analytics identifiers
- Email addresses
- Account identifiers
- Anti-CSRF tokens
- Any value that appears user-specific

Preserve header names, but replace sensitive values with:

```text
[REDACTED]
```

## 10. Phase Four: Evaluate Candidate Endpoints

Implement `endpoint-candidates.ts`.

Build a ranked list of candidate endpoints from:

1. Observed browser traffic
2. Page configuration
3. JavaScript bundle strings
4. Historical endpoint patterns

Each candidate must be classified as:

```text
OBSERVED_CURRENT
DISCOVERED_IN_CURRENT_CODE
HISTORICAL_UNVERIFIED
INFERRED
REJECTED
```

Use a data structure similar to:

```ts
export interface EndpointCandidate {
  id: string;
  classification:
    | "OBSERVED_CURRENT"
    | "DISCOVERED_IN_CURRENT_CODE"
    | "HISTORICAL_UNVERIFIED"
    | "INFERRED"
    | "REJECTED";
  purpose:
    | "movie-search"
    | "theatre-search"
    | "bookable-dates"
    | "showtimes"
    | "session-details"
    | "formats"
    | "unknown";
  method: string;
  urlTemplate: string;
  requiredParameters: string[];
  requiredHeaders: string[];
  requiresCookies: boolean | null;
  evidence: string[];
  confidence: "high" | "medium" | "low";
}
```

Never present a historical endpoint as confirmed.

## 11. Phase Five: Reproduce the Endpoint Outside the Browser

Implement `smoke-test.ts`.

The smoke test must take the highest-confidence observed candidate and attempt to call it using plain server-side HTTP.

### 11.1 Reproduction sequence

Try requests progressively.

#### Attempt A: Minimal request

Use:

```http
Accept: application/json
User-Agent: a descriptive smoke-test user agent
```

#### Attempt B: Normal public browser headers

Add only headers shown to be necessary, such as:

```http
Accept-Language: en-CA,en;q=0.9
Origin: https://www.cineplex.com
Referer: https://www.cineplex.com/
```

#### Attempt C: Non-authentication configuration headers

Add current public configuration headers observed in the website, but only when they do not contain secrets or user-specific values.

Do not copy:

- Authentication credentials
- Account cookies
- Session cookies
- CAPTCHA tokens
- Private or expiring user tokens

### 11.2 Record each attempt

Write:

```text
output/smoke-test-results.json
```

Example:

```json
{
  "endpoint": "observed endpoint",
  "attempts": [
    {
      "name": "minimal",
      "status": 200,
      "contentType": "application/json",
      "parseSucceeded": true,
      "requiresCookies": false,
      "durationMs": 214,
      "resultSummary": "Returned showtime records"
    }
  ]
}
```

## 14. Matching Rules

### 14.1 Movie matching

Normalize:

- Case
- Apostrophes
- Punctuation
- Repeated whitespace
- Leading articles only for secondary comparison

Require an exact normalized title match unless the response also supplies another strong identifier such as:

- Release year
- Cineplex film ID from the matched movie page
- Official movie URL
- Distributor metadata

Do not confuse Christopher Nolan’s *The Odyssey* with other films using the same title.

### 14.2 Theatre matching

The initial theatre match must satisfy:

```text
Name contains: Scotiabank Theatre
City: Toronto
Province: Ontario
```

Prefer an exact current Cineplex theatre-page match.

### 14.3 Format matching

A target format of `IMAX` should match normalized presentation names such as:

```text
IMAX
IMAX 2D
IMAX 3D
IMAX 70MM
IMAX 70MM FILM
IMAX WITH LASER
```

It must not match a record merely because the movie description or theatre amenities mention IMAX.

The format must be associated with the specific screening or auditorium.

### 14.4 Public availability

A screening is considered publicly available only when at least one of the following is true:

- The API marks it as bookable
- A working public booking URL is present
- A session or performance record is returned by the public showtime endpoint with an active sales status

A movie page, release date, theatre listing, or “coming soon” entry alone is not sufficient.

## 15. Stable Screening Identity

Determine the most stable available identifier in this order:

1. Cineplex session ID
2. Performance ID
3. Vista session ID
4. Booking URL containing a stable session identifier
5. Composite key

Fallback composite key:

```text
movieId
+ theatreId
+ startsAt
+ experienceName
+ auditoriumName
```

Hash the normalized composite value using SHA-256.

Do not use seat inventory or seat counts as part of the primary screening identity.

## 19. Acceptance Criteria

The exploration is successful when all of the following are true:

1. The agent identifies the current Cineplex movie and theatre pages.
2. Network requests are captured from the current website.
3. At least one candidate endpoint is identified for bookable dates or showtimes.
4. The endpoint is called from a plain server-side script.
5. The response is saved and parsed.
6. The target film and theatre are resolved without hard-coded IDs.
7. The result can filter screening-level presentation data for IMAX.
8. The output distinguishes:
   - Endpoint failure
   - No matching screenings
   - Matching public screenings
9. Sensitive browser data is not saved.
10. Findings are documented with evidence.
11. All candidate endpoints are clearly classified by confidence.
12. The project runs using documented commands from a clean checkout.

## 20. Minimum Viable Implementation

Do not overbuild the first pass.

The first working version only needs to:

1. Open the current Cineplex movie or theatre page with Playwright.
2. Capture JSON XHR or fetch responses.
3. Identify the response containing showtimes or bookable dates.
4. Save a sanitized example.
5. Reproduce that request with `fetch`.
6. Print whether any matching IMAX screenings exist.

Do not implement:

- SMS
- Persistent scheduling
- Databases
- User accounts
- Multiple users
- Seat-map monitoring
- Seat-quality evaluation
- Automatic purchase
- A mobile application
- A public API

Those belong in a later phase.

## 22. Implementation Guidance

### Discovery-first rule

Do not begin by guessing endpoint paths.

First observe the current website. Only use guessed or historical URLs to supplement the observed evidence.

### Schema-flexible parsing

The initial parser should tolerate different field names.

Possible raw field variants include:

```text
filmId
filmID
movieId
theatreId
theaterId
locationId
siteId
cinemaId
sessionId
performanceId
showtime
startTime
showTime
businessDate
experience
presentation
format
attribute
isBookable
bookingUrl
salesStatus
```

Use recursive inspection during exploration, but produce a clear normalization layer once the relevant schema is identified.

### Time zones

Treat Toronto screening times as:

```text
America/Toronto
```

Do not assume a fixed UTC offset because daylight-saving time changes.

### Logging

Logs must explain:

- What page was opened
- What candidate endpoint was observed
- Why it was selected
- Whether it worked without cookies
- Which fields indicate film, theatre, time, format, and bookability

Do not log entire large payloads to the console.
